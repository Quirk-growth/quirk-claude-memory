Quando várias sessões/chats do Claude Code rodam apontando pro mesmo diretório de projeto no disco (ex.: `/Users/renanreal/area-membros-quirk-crm`), elas compartilham literalmente o mesmo `.git` local — não é só "várias sessões editando o mesmo repo remoto", é o mesmo checkout físico. Isso significa: se a Sessão A faz commits locais (mesmo sem dar `git push`) e a Sessão B, trabalhando numa feature diferente, roda `git fetch`/`git merge origin/main` seguido de `git push`, o push da Sessão B leva junto TODOS os commits da Sessão A que estavam alcançáveis pelo HEAD compartilhado — mesmo que a Sessão A nunca tenha pedido push nem tenha terminado sua checklist de deploy.

**Como isso apareceu**: em 12/ago/2026, terminei toda a revisão (per-task + whole-branch, 2 rodadas) da feature "dono/gerente vira vendedor de si mesmo" e estava prestes a dar `git push` depois da checagem final de testes. Ao reconferir `origin/main` antes do push, descobri que meus commits (`77aa9d5` etc.) já estavam lá — outra sessão paralela, trabalhando na feature "painel de atividade do lead" (construída em cima do meu código), já tinha dado push e levado minha feature junto. Confirmei via Render (`Deploy live for 54fcc11`) que já estava em produção. Não havia nada pra eu empurrar.

**Sintoma relacionado**: durante essa mesma investigação, `origin/main` avançou 3 vezes em menos de 2h (3 sessões diferentes empurrando features distintas em paralelo: perfil/agenda, emails do comercial, e a de painel de atividade). Cada vez que eu rodava a suíte completa de testes, ela travava em massa (95-104 arquivos falhando) num prompt interativo do Drizzle ("Accept warnings and push schema to database? y/N") que nunca é respondido em processo não-interativo — muito provavelmente contenção no banco de teste compartilhado sob push concorrente de múltiplas sessões rodando suíte ao mesmo tempo, não um bug real de código (ver [[reference_suite_testes_area_membros]]).

**Como aplicar**:
- Antes de dar push "porque já terminei minha checklist", sempre confira primeiro se `origin/main` já não CONTÉM seus commits (`git merge-base --is-ancestor <seu-ultimo-commit> origin/main`) — outra sessão pode já ter levado seu trabalho.
- Se `origin/main` avançou bastante desde o último fetch, é sinal de que várias sessões estão ativas em paralelo agora — nesse cenário, falhas em massa e não-correlacionadas na suíte de testes completa são mais prováveis de ser infra compartilhada (banco de teste, contenção) do que uma regressão real; separar isso exige checar se o padrão de falha é idêntico antes/depois das mudanças de cada sessão, e se os arquivos de teste que tocam SEU código especificamente continuam passando isolados.
- Verificar deploy "no ar" sempre pelo Render (evento "Deploy live for `<hash>`") + smoke test num endpoint específico da mudança — nunca assumir que "eu não dei push" significa "não está em produção".

**Gotcha do mesmo tipo, mas com `.superpowers/sdd/` (arquivos de plano SDD)** (26/ago/2026): ao rodar `subagent-driven-development` numa feature nova ("permissões configuráveis"), a Task 8 desse plano leu `.superpowers/sdd/task-8-report.md` e encontrou o relatório de uma Task 8 de OUTRA feature (BI Comercial), já concluída dias antes na mesma sessão — os nomes `task-N-brief.md`/`task-N-report.md`/`review-BASE..HEAD.diff` que os scripts do skill escrevem em `.superpowers/sdd/` NÃO são isolados por plano nem por sessão: é um namespace plano, achatado, compartilhado por QUALQUER plano que já passou por esse diretório (e, com múltiplas sessões paralelas ativas como neste repo, potencialmente por planos rodando AGORA em outro chat). Um número de task igual em dois planos diferentes colide. Nenhum dado foi perdido (o conteúdo antigo só foi lido por engano antes de eu sobrescrever com o relatório certo), mas o revisor quase leu o relatório errado. **Regra**: antes de confiar no conteúdo de um `task-N-report.md`/`task-N-brief.md` já existente neste diretório, confirme que ele é da FEATURE atual (o título/primeira linha do arquivo deveria bater com o plano em andamento) — se não bater, é sobra de outro plano, sobrescreva sem medo (o `progress.md` — esse sim, por ser um ledger acumulativo com nome fixo por sessão de trabalho — é a fonte de verdade real, não os `task-N-*.md` individuais).

**Conflito de merge real entre duas features paralelas** (26/ago/2026): terminei a feature "Permissões configuráveis" inteira (24 commits locais, nunca dado push) e, ao sincronizar antes do push, `origin/main` já tinha avançado 13 commits de outra sessão (feature "guia comercial" + "propostas comerciais", já mergeada e em produção). As duas mexeram no MESMO arquivo (`src/lib/menuAdmin.ts`) de formas incompatíveis: minha feature reescreveu `secoesDoAdmin`/`itensDoColaborador` de síncronas-por-papel pra assíncronas-por-matriz (Task 5, semanas antes); a outra feature, sem nunca ter visto meus commits, estendeu a versão SÍNCRONA antiga com uma regra de negócio nova (comercial alcança "Meu treinamento" via `podeVerGuia`, não só `fazTrilha`) e um item de menu novo (`/propostas`, fora do namespace `/admin/*`, com gate próprio). `git merge origin/main` gerou 2 conflitos reais (não só drift de linha) — resolvi manualmente preservando a ARQUITETURA da minha feature (assíncrona, matriz) e a REGRA DE NEGÓCIO da outra (a condição `fazTrilha||podeVerGuia`, o item `/propostas` com force-add replicando o gate real da página), removi uma função duplicada que o merge automático deixou órfã, ajustei os testes conflitantes pra refletir a reconciliação, rodei a suíte inteira antes e depois (mesmas 3 falhas pré-existentes, nenhuma nova) e só então completei o commit de merge. Mandei o resultado pra revisão adversarial separada antes do push, focada só no diff da resolução (`git show --cc <merge-commit>` isola exatamente as escolhas de merge, sem re-revisar o conteúdo que já vinha limpo de cada lado). **Regra**: antes de dar push de uma feature grande e antiga (muitos commits, muito tempo sem sincronizar), sempre `git fetch` + checar se `origin/main` divergiu — se sim, `git merge` (não force-push, não descartar o lado do outro) ANTES do push, resolvendo conflito por conflito com o mesmo cuidado de uma implementação nova (entender a intenção dos dois lados, não só pegar um "the ours"/"theirs" no automático), e tratar a resolução do merge como código que precisa de revisão própria antes de subir.

**Gotcha do mesmo tipo, mas com `git stash`** (25/ago/2026, subagent da feature "permissões configuráveis"): um `git stash && ... && git stash pop` genérico (sem argumentos) pra isolar mudanças untracked acabou aplicando o stash de OUTRA sessão paralela (`stash@{0}: On feat/onboarding-administrativo: WIP: 6 achados...`), gerando conflito de merge em 4 arquivos de uma feature completamente diferente (importação do Guia). Como deu conflito (não aplicou limpo), o Git NÃO descartou o stash original — ele ficou intacto em `stash@{0}`; o subagent só reverteu os 4 arquivos conflitantes pro estado de `HEAD` (sem tocar no stash) e confirmou com `git stash list` que nada sumiu. Sem perda de dado, mas só por sorte do conflito ter acontecido (um pop LIMPO teria aplicado e potencialmente descartado o stash da outra sessão). **Regra**: neste repo, nunca usar `git stash`/`git stash pop` sem argumento explícito (índice `stash@{N}` ou pathspec `--`) — com múltiplas sessões ativas, um stash "genérico" pode manipular o de outra sessão. Já havia evidência de outra sessão tendo passado pelo mesmo problema antes (`stash@{1}: "devolvendo: nao pertence a esta sessao (restaurado sem querer via stash pop)"`) — não é caso isolado.

**Gotcha do mesmo tipo, mas com `git checkout` de outra sessão trocando o branch corrente por baixo do meu (27/ago/2026):** pulei minha própria disciplina de checar branch/divergência antes de escrever um spec+plano novo (fui direto de `Write`/`git commit` sem `git status`/`git branch --show-current` primeiro) — e enquanto eu escrevia, outra sessão paralela deu `git checkout` numa branch completamente diferente (`feat/gerador-propostas`, de outra feature dela) NESTE MESMO diretório compartilhado. Meus 4 commits de doc (spec+plano da bolinha de status) foram parar empilhados em cima do trabalho dela, numa branch com nome que não tinha nada a ver com o que eu estava fazendo — só descobri ao checar `git branch --show-current` bem depois, já com os commits feitos. Recuperação sem perda: `git branch --contains <meu-commit>` confirmou que só a branch errada continha meus commits; criei a branch certa a partir do `origin/main` atual (`git checkout -b <nome-certo> origin/main`), `git cherry-pick` dos meus 4 commits pra lá (limpo, sem conflito — só docs), e `git branch -f feat/gerador-propostas <tip-original-dela>` pra devolver a branch da outra sessão exatamente como estava (o `git branch -f` é seguro porque a branch-alvo não estava com checkout ativo no momento — não mexe em working tree). **Regra reforçada**: SEMPRE `git status --porcelain` + `git branch --show-current` como o PRIMEIRO passo de qualquer trabalho novo neste repo — mesmo pra "só escrever um spec", nunca assumir que o branch corrente é o que eu esperava, porque outra sessão pode trocá-lo a qualquer momento entre uma ferramenta e outra.

**Conflito de merge do tipo "outra sessão generalizou meu componente" (29/ago/2026, deploy do Motor de Formulários):** ao sincronizar 22 commits locais (feature nova, nunca dado push) com `origin/main`, que tinha avançado 56 commits de outras sessões, um dos 5 conflitos reais foi em `TarefasFiltros.tsx` — eu tinha construído `CampoClienteFiltro.tsx` (componente bespoke, campo de cliente com busca) numa feature anterior desta mesma sessão; enquanto isso, outra sessão paralela generalizou a MESMA ideia num componente reutilizável (`SeletorBusca.tsx`) e o aplicou em TODOS os campos da mesma barra de filtro (Responsável/Autor/Etiqueta/Prioridade/Cliente) — inclusive corrigindo, de brinde, uma race condition de staleness no debounce da busca por título que minha versão nem sabia que tinha (closure fechando sobre `searchParams` obsoleto se outro filtro disparasse `router.push` no meio do debounce). Resolução: adotei a versão deles por inteiro (não só o campo Cliente — TODOS os campos da barra já usavam `SeletorBusca` vindos de fora dos marcadores de conflito, então manter meu componente só pro Cliente teria deixado a barra inconsistente), aposentei (`git rm`) meu `CampoClienteFiltro.tsx` e seu teste por ficarem genuinamente órfãos, e troquei o arquivo de teste conflitante inteiro pela versão deles (`git checkout --theirs`) em vez de tentar remendar — já que meus testes validavam detalhes internos de uma implementação que deixou de existir. **Regra**: quando o conflito é "eu construí uma coisa específica, a outra sessão generalizou o mesmo padrão", geralmente vale mais a pena adotar a generalização por inteiro (inclusive os testes dela) do que tentar preservar o componente antigo só numa ponta — sobretudo se a versão nova corrige um bug real que a antiga tinha. Verificar antes que o componente antigo não é usado em mais nenhum lugar (`grep -rln`) antes de deletar.

**Worktree "principal" (dono do `.git` compartilhado) em uso por outra sessão no momento de um merge local (30/ago/2026, redesign do Motor de Formulários):** ao terminar uma feature numa branch própria (`feat/motor-formularios-redesign`, criada dentro do worktree persistente `area-membros-quirk-crm`) e o usuário pedir "merge local pra main", o fluxo padrão da skill `finishing-a-development-branch` assume que dá pra fazer `git checkout main` no worktree raiz do repo (dono do `.git-common-dir`) pra rodar o merge lá. Neste repo isso é perigoso: o worktree raiz (`/Users/renanreal/area-membros-quirk`) não é um clone "limpo" reservado só pra merges — é ele mesmo um worktree de trabalho ativo, e no momento estava em outra branch (`feat/busca-filtros-tarefas`) com arquivos não commitados de outra sessão paralela. Fazer checkout ali teria trocado o branch corrente debaixo dos pés dela. **Como resolvi**: como o merge era um fast-forward puro (a `main` local já era ancestral direta da branch da feature — confirmado com `git merge-base --is-ancestor main HEAD` antes de qualquer coisa), atualizei a ref de `main` direto (`git branch -f main <tip-da-feature>`), sem checkout em NENHUM worktree — plumbing puro, zero risco pra qualquer sessão. Também não deletei a branch da feature depois (a skill padrão manda `git branch -d`), porque ela é literalmente a identidade do worktree onde eu estava trabalhando (`area-membros-quirk-crm`) — apagá-la ali quebraria o workspace do usuário sem necessidade nenhuma. **Regra**: neste repo, "merge local" nunca deve assumir que existe um worktree neutro reservado só pra isso — sempre checar `git worktree list` + `git -C <worktree-raiz> branch --show-current` + `git -C <worktree-raiz> status --porcelain` ANTES de tentar checkout de qualquer branch no worktree raiz; se não for fast-forward puro (precisar de merge de verdade, não só mover a ref), a alternativa seria criar um worktree temporário só pra isso (`git worktree add`), nunca reaproveitar um worktree que outra sessão possa estar usando.

**A alternativa prevista acima foi exercitada de verdade horas depois, mesma sessão (30/ago/2026, deploy do dashboard de respostas):** desta vez `origin/main` tinha avançado com uma feature de outra sessão (Painel Auto Ads, via PR) — não dava mais pra só mover a ref de `main`, precisava de um merge de verdade. Receita que funcionou, sem tocar em nenhum worktree em uso por outra sessão: `git worktree add /tmp/merge-scratch-X origin/main --detach` (worktree descartável, fora de `.worktrees/`/`worktrees/`, então cleanup é meu mesmo); `cd` nele e `git merge --no-ff <minha-branch> -m "..."`; **antes de rodar `tsc`/testes ali, `ln -s <worktree-real>/node_modules node_modules`** dentro do scratch — evita um `npm install` completo (lento) só pra validar o resultado do merge, já que o `node_modules` do worktree de origem é compatível (mesmo `package-lock.json`); depois de verificar (`npx tsc --noEmit` limpo), `git branch -f main <sha-do-merge>` a partir do worktree real (não do scratch) pra mover a ref; por fim `git worktree remove /tmp/merge-scratch-X --force` + `git worktree prune`. Confirmei de antemão que dava pra ser um merge limpo checando `comm -12` entre `git diff --name-only <base>..<minha-branch>` e `git diff --name-only <base>..origin/main` — zero interseção de arquivos = merge sem conflito garantido antes mesmo de tentar. **Regra reforçada**: o truque do symlink de `node_modules` é o que torna essa técnica prática (sem ele, validar um merge feito num worktree descartável exigiria reinstalar tudo); funciona porque worktrees do mesmo repo compartilham o mesmo `package-lock.json` na maioria dos casos — confirmar isso antes de confiar no symlink se os branches mexerem em `package.json`.

**Checar branch uma vez no início não basta (02/set/2026, fix de segurança em `Clientes.travasClientes`):** fiz tudo certo no começo — `git switch feat/tela-inicial-cliente` confirmado por output ("Switched to branch..."). Mas entre esse switch e o `git commit` (uns 40min depois, rodando suíte completa em background), outra sessão paralela mergeou essa MESMA branch em `main` local E deu checkout em `main` neste worktree compartilhado — meu commit acabou empilhado em cima do merge dela, na branch `main`, sem eu perceber até o output do commit mostrar `[main <sha>]` em vez do nome esperado. Sem perda (a outra sessão já tinha, coincidentemente, dado push desse merge+DDL pra produção antes de mim), mas só por sorte. **Regra reforçada**: neste repo, `git branch --show-current` verificado no INÍCIO de uma tarefa não garante nada no FIM dela, se houver qualquer operação longa (suíte de testes, espera de deploy) no meio — reconferir branch imediatamente antes de QUALQUER `git commit`/`git push`, não só uma vez por tarefa.
